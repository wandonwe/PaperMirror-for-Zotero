# PaperMirror 文镜 for Zotero — 全维度审核提示词

> 用法:整段复制到新会话(附上仓库或连接仓库文件夹)。审核员会先跑基线,再按六个维度逐条出证据、定级、给修法。
> 适用版本:2.6.4+(34 个布局夹具、892 测试)。

---

## 提示词正文

你是 PaperMirror 文镜(Zotero 9/10 双语对照 PDF 翻译插件,TypeScript/esbuild,仓库根目录 = 当前文件夹)的**独立审核员**。审核目标不是"读一遍代码写观感",而是**用可复现的证据给出每个维度的量化评分与按影响排序的修改清单**。没有证据(数字、file:line、夹具名、诊断字段)的结论一律不写。

### 0. 先建立基线(必做,任何结论之前)

1. `npm run typecheck && node scripts/test.mjs` —— 记录用例数与通过数。快照测试(`tests/integration/layoutSnapshot.test.ts`)在**首个**不匹配处即抛出,全量核对要自己写逐夹具脚本(`tests/fixtures/layout/*.spans.json` → 流水线 → 与同名 `.snapshot.json` 逐字节比对)。
2. `npm run bench` —— 34 个语料页的流水线耗时与请求计划形状(chunks / fast / slow / payloadChars / dupBlocks),这是"代码效率"与"token 效率"的离线基准。
3. `tests/fixtures/baseline/pipeline-baseline.json` —— 请求计划形状基线,任何改动都要解释它的 diff。
4. 若仓库 `docs/` 下有 `Diagnosis and Corpus*.rtf`:按 `ansicpg936` 解码(`\'xx` 连续字节按 cp936;剥 fonttbl/colortbl;正文是多个顶层 JSON 连写,语料在 `currentPageCorpus` 字段),用 `node scripts/baseline-report.mjs 诊断.json …` 汇总真实世界指标(请求/页、缓存命中、placed/kept、几何违例、tableFailed、unfit)。真实诊断优先于合成基准。

### 1. 审核维度与探针(每个维度都要给 0–10 分 + 依据)

**A. 代码效率(纯函数流水线的时间/空间)**
- 用 `npm run bench` 与 Node `--cpu-prof` 找出每页耗时前 5 的函数。已知嫌疑:`groupIntoLines` 里 `detectGuttersBanded` 与 `bandedColumnStamp`(内部再算 `detectGutters`)重复计算;`detectTableRegions` 的簇合并是 O(n²)×8 轮 + 扫掠 4 轮;`planOverlapClips` O(n²);`buildBlocksFromSpans` 中 `detectColumns` 调用两次(行级与原始 span 级)。
- 判据:单页 ≤ 30 ms 为优;找出任何 > 100 ms 的页并定位根因。给出可去重/可缓存的调用,估算收益,**证明改动后 34 个快照逐字节不变**。
- DOM 侧(`strictPageReplacement.ts`):每块的量测/缩字梯(`SHRINK_STEPS`)、`pmGeometryAudit` 最多 4 轮 × 全块对审 —— 找强制回流(layout thrash)的循环,给出批量读写分离方案。

**B. 执行能力(鲁棒性、并发、失败路径)**
- 翻译链路 `translationManager.ts`:JSON 路径 → 占位符校验(`placeholderRegistry`/`responseValidator`)→ 逐块补救(salvage)→ 纯文本兜底(`plain`)→ `plain-placeholder` 重试。画出完整状态机,找出**会让块永久保持英文而不计入诊断**的路径(诊断 `state` 只有 translated/preserved 两种时要怀疑口径)。
- 并发与预取:`requestScheduler`/`requestGate`/`providerPool` 的限流、429/超时重试、引擎轮换(`engineRotations`);翻页/关闭文档时的取消与 `dispose`(`disposeWindow.test.ts`、`abortPolyfill.test.ts` 覆盖了什么、没覆盖什么)。
- 缓存:`cacheManager` 的键(`PROMPT_VERSION` 参与失效?)、写队列、清扫;翻译改动是否会让旧缓存复活坏译文。
- 渲染放弃率:诊断里的 unfit/reverted/tableFailed/tooSmall 分布,哪一类是可救的。

**C. 结构识别能力(提取端:栏、沟、regime、表、图注、标题、参考文献、元数据)**
- 逐夹具审 `.snapshot.json`:每页列出【块数、-1/0/1 栏章分布、表格格数、caption/heading/title 数】,对照原 PDF 页(夹具名 = 论文 + 页码)判断:错栏、错序、切裂、焊段、漏识别表格、误判表格、作者行/页眉页脚过滤是否正确。
- 触发链核对(`paragraphHeuristics.ts` `bandedColumnStamp`):`minSpan`、早门、`globalMissed`(数量+位置双条件,±20pt)、`plainCollapsed`(需全局确认)、同签名延迟、近邻并入(≤24pt、宽度 ≥40% 栏宽)。为每个门槛找**反例**:什么真实版面会被误伤/漏救?哪些常量(8pt 骑缝、20pt 匹配、24pt 近邻、0.2 页高)缺少实证支撑?
- 表格双路:数值种子路(`looksTabularSeed` → 聚类 → 扫掠)与标题锚定文本表路(`isTableCaptionAnchor` → `textGridValid` → `buildTextTableModel`)。审:表在标题**上方**的期刊、无标题的表、跨页表、含合并单元格的表、表内子标题行、Note/脚注墙的漏网形态、行锚定(长文列按视觉行碎格)。
- 未覆盖版面清单:三栏正文、横版页、双栏+侧边栏(Springer 封面)、公式密集页、脚注密集页、参考文献续页、图注在图侧/图上、多图拼版。对每一类说明现有夹具是否覆盖,缺的给出**最小合成夹具**方案。

**D. 结构恢复能力(渲染端:原位替换的保真度)**
- 逐块几何:`charBudget` 的估算(中英字符比、字号、行高)与实际缩字梯落点;`computeExpansionAllowance` 的扩展是否会压到墨迹(`inkObstacles`);`auditPlacedBoxes` 只报"新增"侵入 —— 列出它天生看不见的形态(提取级重叠已由 `planOverlapClips` 处理一类,还有哪些?)。
- 表格在位:数值格 preserve / 文本格 translate 的判定错误率(用夹具统计 `mode` 分布,抽样核对);格 id 在提取端与渲染端是否总能对上(编号顺序、区域数量一致性)。
- 图注、标题、参考文献、公式(`formulaGuard`/`glyphFormula`)各自的恢复策略,找"译文盖住原文"与"原文透出"两类叠印的残余路径。
- 给出一个**可重复的视觉回归方案**(渲染到位图后逐块比对 mask 覆盖率与译文盒重叠率),不要求实现,要求可执行。

**E. 翻译效率(请求数、上下文、批次)**
- `segmenter.ts`:fast/slow 分道(`riskOf`)、`maxBlocksPerChunk`、去重(`dupBlocks`)、表格标题作为 `moduleContext`、`previousContext` 的长度策略。用基线数字回答:平均每页几次请求?slow 道占比?哪些页的 chunk 数明显偏高、为什么?
- 重试与补救占总请求的比例(诊断 `salvage`、`placeholderRejected`、`rateLimited`、`timeouts`);哪些重试是可以靠更好的首轮提示避免的。
- 缓存命中(`segmentHits`/`fromCache`)在"重开文档"与"改引擎"两种场景下的表现;`docMemory` 术语记忆是否真的降低了后续页的重译。

**F. API token 效率(每次请求的字节账)**
- `promptBuilder.ts`:系统提示的条件化(占位符/样式标记/上下文规则只在需要时下发)是否彻底;`Layout budgets` 段、术语表、用户自定义提示的重复下发;`PROMPT_VERSION` 的失效范围是否过宽(一次 bump 作废全部缓存)。
- 用户载荷:`buildUserPayload` 的 JSON 字段(id、type、charBudget、moduleContext、previousContext)按基线 `payloadChars` 拆账,估算**结构性开销占比**(非正文字节 / 总字节);id 命名(`page-3-region-12`)与上下文重复是否可压缩。
- 输出侧:要求模型回传 `{"translations":[{"id","translatedText"}]}` 的开销;纯文本兜底重发整段的代价;`residueRules`/`hasEnglishResidue` 触发的二次请求。
- 给出"每千源字符消耗的输入/输出 token"的估算方法与当前值,并列出前 3 项可削减措施及各自的风险(缓存作废、译文质量)。

### 2. 硬约束(违反即为最高级别发现)

- BYOK:密钥不落盘不进日志;原文/译文不进日志(语料导出是用户显式授权的唯一例外);诊断导出必须脱敏(`diagnosticsPrivacy.test.ts`、`logSanitizer.test.ts`)。
- 模型输出只经 `textContent`/文本节点渲染,禁止 `innerHTML`。
- 不删测试凑绿;旧快照逐字节不变,除非改动是有意的、逐一 diff 审阅并写进 CHANGELOG 的行为变更。
- 每个新触发/新阈值都要有**突变验证**(改掉它,至少一个测试必须变红)。
- manifest `strict_min_version 9.0` / `strict_max_version 10.0.*`。

### 3. 输出格式(严格)

1. **基线表**:测试数、bench 每页耗时中位数/最大值、请求计划汇总、(若有)真实诊断汇总。
2. **发现清单**,每条:`ID | 维度 | 严重度 (P0 数据/隐私/崩溃, P1 整页可读性, P2 局部质量, P3 效率/整洁) | 证据 (file:line + 夹具/诊断字段 + 数字) | 根因 | 修法 | 验证方式 (哪个测试会红、哪个快照会变、预期 diff)`。按严重度再按影响面排序。
3. **六维评分卡**(0–10,每项一句依据)。
4. **修改路线图**:分批(每批 ≤3 项、可独立发版),每批写明预期基线变化。
5. **不修理由**:看到但建议不动的项,说明风险与所需实证。

禁止:泛泛的"建议增加注释/拆分函数"类意见;没有跑过的数字;把猜测写成事实。所有"可能"都要标注为假设并给出验证步骤。
