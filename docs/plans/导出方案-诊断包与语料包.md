# 导出方案:独立的「诊断文件」与「翻译语料」入口

> 状态:**方案,未实现**。本文只整理设计与取舍,不含代码改动。
> 依据:用户 2026-09-08 的需求 + 对当前实现(2.8.4)的逐项核对。

---

## 0. 结论先行

方案整体可行,但有一处**硬问题**必须先定策略,否则语料包会变成"看起来完整、其实是
事后重新解析的东西":

> **spans 现在根本没有被留存。** `layoutCorpus()` 取的是 `adapter.getTextLayerItems()`
> —— 阅读器**渲染过的页**才有文本层,非当前页拿不到;而 `buildBlocksFromSpans` 消费
> 完 spans 之后只留下结构块,原始 spans 当场丢弃。所以"导出所有已处理页的 spans"
> 只能在导出时**重新解析**,不可能拿出翻译当时的那一份。

按用户定的规矩,这必须**明确标记,不能冒充**。第 3 节给出标记与自检方案。

另外两点值得先说,因为它们决定了工作量分配:

- **诊断包几乎不受内存淘汰影响**。页状态、页级指标、`placement` / `geometryAudits` /
  `abandonedBlocks` / `placementProbe` 都不随 2.8.3 的淘汰丢失。唯一会缺的是**每块
  状态明细**(`state.blocks` 被卸)与 `keepOrigin` / `rejectReasons`(淘汰时清掉)。
  → 诊断包风险最低,应当先做。
- **ZIP 不能引依赖**(项目硬约束:不引入新依赖)。两条路,见第 5 节。

## 1. 数据来源盘点(逐字段核对过现有实现)

| 数据 | 现在存在哪 | 页被淘汰后还在吗 | 导出时的可得性 |
|---|---|---|---|
| **spans**(原始文本项 + 坐标) | **不留存**。`getTextLayerItems` 只对渲染过的页有;`getPageData` 可重解析任意页 | — | **只能重新解析**,必须标记 |
| 结构块 `blocks`(id / 类型 / boundingBox / lineRectsPdf / column / tableRow·tableCol / translationMode) | `state.blocks` | ❌ 被卸 | 重新抽取可重建(同构建、同代码路径,但不是当时那一份) |
| 译文 `translations` | `state.translations` | ❌ 被卸 | 页缓存恢复(仅 `cached === true` 的页) |
| 页状态 / 页级指标(requests、attempts、耗时、时序三段、token) | `state.status` / `state.diagnostics` | ✅ 保留 | 直接可得 |
| 排版结果(replaceable / committed / abandoned / inkBlocked / layoutMs) | `readerSession.placementStats` | ✅ 不受淘汰影响 | 直接可得 |
| 放弃原因(逐块 `abandonReason`) | `readerSession.abandonedBlocks` | ✅ | 直接可得 |
| 几何审计 | `readerSession.geometryAudits` | ✅ | 直接可得 |
| 排版探针(逐块像素盒 + baseInk/maskOpaque) | `readerSession.placementProbe` | ✅(仅开调试日志时采样) | 直接可得 |
| 每块状态明细(translated / preserved / unplaced) | 由 `state.blocks` 现算 | ❌ 随 blocks 一起没 | 需重建或标缺失 |
| `keepOrigin` / `rejectReasons` | `state.keepOrigin` / `state.rejectReasons` | ❌ **2.8.3 淘汰时显式清掉** | 需重建或标缺失 |
| 会话级用量与计量(usage / render / cacheWrites) | manager + pane + cacheManager | ✅ | 直接可得 |

> 这张表本身就是用户那句"如果当前实现没有保留某阶段数据,应明确标记"的答案:
> **spans 一定是重新解析的;blocks / translations / 每块状态在被淘汰的页上是恢复的
> 或缺失的;其余都是当时那一份。**

## 2. 导出范围与一致性快照

### 范围
- 当前文档、**本次会话中所有已处理页面**(manager 的页表里有记录的页),不限当前页。
- 已完成 / 部分完成 / 失败 / 正在翻译 —— 全部纳入,各自记状态。
- **未处理页只记状态,绝不为了导出发起翻译。** 未处理页在 `summary.json` 里以
  `notProcessed` 计数出现,`pages/` 目录里不生成文件(或生成只含状态的极简文件,
  见第 4 节的开放问题)。

### 快照策略(诚实版)
真正的"整篇原子快照"要么把全文装进内存(违背分批写入),要么锁住翻译(违背"后续
翻译继续进行")。所以采用:

1. 导出开始记 `snapshotAt`,**冻结页清单与各页状态**(浅拷贝一份页号 + 状态 + 是否
   已淘汰);
2. **暂停内存淘汰**(`exportHold` 引用计数,导出期间 `evictColdPages` 直接返回)——
   避免刚决定要导的页在写到它之前被卸掉;
3. 逐页读取、逐页写出,每页记自己的 `readAt`;
4. `manifest.json` 写明 `snapshotPolicy: "page-at-a-time"` 与 `snapshotAt`,
   **不谎称整体原子**;
5. 导出期间新完成的页不回填已写出的部分,`summary.json` 记 `pagesStillTranslating`。

### 淘汰过的页怎么恢复
- **诊断包不需要恢复**:它要的东西基本都不随淘汰丢(见第 1 节),只有"每块状态明细"
  会缺 → 直接标缺失,不为它做恢复。
- **语料包需要恢复**:重新抽取(PDF 解析,**无 API 调用**)得到 blocks,再读页缓存
  得到译文。恢复失败(缓存未命中 / 键已变)→ 该页记 `missing`,并计入 manifest。
- **恢复用独立的临时容器,不塞回 `manager.pages`** —— 否则会污染 LRU 与页状态机,
  还可能把一页"复活"成 hot page。这条很重要。

## 3. 缺失与来源的表达(核心:不能静默漏页)

每页文件带一段 `availability`,五个维度各自独立标注:

```json
{
  "page": 12,
  "availability": {
    "spans":        "re-extracted",
    "blocks":       "live",
    "translations": "restored-from-cache",
    "placement":    "live",
    "blockStates":  "missing:evicted"
  },
  "blocksMatch": true
}
```

取值固定为四类:`live`(当时那一份)、`restored-from-cache`、`re-extracted`、
`missing:<原因>`。原因也用枚举:`evicted`、`cache-miss`、`never-processed`、
`extract-failed`、`not-sampled`(探针只在调试日志开启时采样)。

**`blocksMatch` 是给 spans 用的自检**:把重新解析出的 spans 跑一遍
`buildBlocksFromSpans`,与留存的 `state.blocks` 比对块 id 与原文哈希。

- 一致 → `blocksMatch: true`,说明这份重解析的 spans 确实能复现当时的分段;
- 不一致 → `blocksMatch: false` + `blockIdDiff` 计数。**这正是"不能用重新解析的结果
  冒充当时数据"的可验证形式** —— 不匹配时数据仍然导出,但明确告诉审阅者它不是当时
  那一份。

`manifest.json` 汇总:`pagesTotal / processed / complete / partial / failed /
notProcessed / restored / reExtracted / missing`,以及 `blocksMatchFalse` 计数。
**任何一页的任何一个维度缺失,都必须在这里能数出来。**

## 4. 文件格式与命名

### 命名
```
PaperMirror_v2.8.4_diagnostics_20260908_153042_287+0800.zip
PaperMirror_v2.8.4_corpus_20260908_153042_287+0800.zip
```
- 版本**从运行中的插件取**:`startup(params)` 里已经有 `params.version`
  (`bootstrap.js` 传入),导出模块经一个模块级 `pluginVersion()` 读它 ——
  **不读 manifest.json 常量、不硬编码、不从 UI 字符串里抠**。
- 时间:本地时区,日期 + 时分秒 + 毫秒 + `±HHMM` 偏移。
- 重名:追加 `_2`、`_3`,**绝不覆盖**。
- **文件名不含论文标题**(隐私)。文档标识只放在包内 `manifest.json`,且诊断包里
  只放 attachment key 的哈希前缀,不放标题。

### 包内结构
```
manifest.json      版本、导出时间、范围、快照策略、完成/失败/缺失统计
summary.json       会话级汇总(usage / render / cacheWrites / engines 自检 / 放弃原因分布)
pages/
  page-0001.json
  page-0002.json
  ...
```
页文件按 1 基页码补零到 4 位。缺失页**仍然生成文件**(只含 `availability` 与状态)
—— 让"少一个文件"永远不会被误读成"这页没问题"。

## 5. ZIP 的实现路线(不引依赖)

| 方案 | 优点 | 风险 |
|---|---|---|
| **A. 平台 `nsIZipWriter`**(`@mozilla.org/zipwriter;1`) | 有压缩,语料包能小一个数量级;可逐条 `addEntryStream` | **需要在真实 Zotero 里验证可用性**,我在这个环境验证不了 |
| **B. 自写 store-only ZIP**(local header + CRC32 + central directory,约 80 行) | 零依赖、零平台假设、可用 `IOUtils.write(..., {mode:'append'})` 流式追加 | 不压缩 —— 语料包会很大(23 页的 spans 导出已经 2.7 MB) |

**建议:先验证 A,可用就用 A,不可用回落 B。** 语料包的体积差距足够大,值得为 A 花
一次验证。两条路都支持"逐条写入,不把整包装进内存"。

## 6. 交互流程

```
点击导出 → (语料才有)隐私确认 → 选择保存位置 → 进度 → 成功后「显示文件」
```

- 「更多」菜单拆成两项:**导出诊断文件** / **导出翻译语料**;不再复制到剪贴板。
- 菜单项下方说明(用户给的文案):
  > 导出当前文档已处理页面的数据,不会发起额外翻译请求。
- **诊断无需确认**;**语料必须确认**,文案明说"包含论文原文与译文"。
- 保存位置:`nsIFilePicker`(**需验证**);回落 = 写进 Zotero 数据目录下
  `PaperMirror/exports/` 并直接 reveal,同时 toast 告知落点。
- 进度:分三阶段 —— 准备(冻结快照)→ 写入(第 n / N 页)→ 完成。复用状态胶囊或
  toast,不新造 UI。
- **失败只报失败,并指明阶段**(prepare / read-page / write-entry / finalize /
  save),绝不在失败后提示成功。
- 「显示文件」:`Zotero.File.reveal(path)`(**需验证**);不可用则退化为把路径写进
  toast 与日志。

### 导出期间的硬边界
- 不调用任何翻译 API;
- 不清缓存、不刷新翻译、不改任何页状态;
- 只做两件有副作用的事:**暂停淘汰**(导出结束必定恢复,`try/finally`)与**写文件**;
- 重新抽取走的是与翻译同一条 PDF 解析路径,但结果只进临时容器。

## 7. 隐私

**诊断包**
- 沿用现有 `diagnosticsPrivacy` 的哨兵测试口径:原文 / 译文 / 密钥一个字都不能进;
- 新增断言:**文件名不含文档标题**;
- 现在诊断里有 `engines[].endpointHost`(主机名,不含路径与密钥)。用户要求"不含
  敏感请求地址" —— 这一条**需要你拍板**:保留 host(便于区分官方 / 代理 / 本地),
  还是降级成布尔 `customEndpoint: true`。

**语料包**
- `manifest.json` 第一个字段就是 `CONTAINS_SOURCE_TEXT: true`,自我声明;
- 确认对话框 + toast 各提醒一次(与现有「语料」按钮的姿态一致);
- 不含密钥、不含端点 URL、不含用户词表以外的任何配置。

## 8. 分期建议

| 期 | 内容 | 理由 |
|---|---|---|
| **P1** | 诊断包(全页范围、manifest / summary / pages、命名、store-only ZIP 兜底) | 不碰 spans 难题,不需要恢复淘汰页,风险最低,立刻可用 |
| **P2** | 语料包(spans 重解析 + `blocksMatch` 自检 + 从缓存恢复 + 缺失标注) | 依赖 P1 的打包与命名骨架 |
| **P3** | 平台交互(FilePicker / reveal / nsIZipWriter 压缩) | 三个 API 都需要在真实 Zotero 里验证,失败有明确回落 |

每期照旧:单测 + 突变验证 + 结构闸;导出路径不碰提取 / 结构 / 排版,快照与请求计划
基线必须逐字节不变。

## 9. 需要你拍板的四件事

1. **spans 策略**:接受"导出时重新解析 + 标 `re-extracted` + 用 `blocksMatch` 自检"
   吗?这是唯一诚实可行的路。另一条路是**开始留存 spans**,但那会与 2.8.3 刚做的内存
   淘汰直接对冲(spans 比 blocks 还大),我不建议。
2. **`keepOrigin` / `rejectReasons`**:2.8.3 淘汰时把它们清掉了。要为诊断完整性改成
   保留吗(每页几百字节,很小),还是接受标 `missing:evicted`?
3. **`endpointHost` 算不算"敏感请求地址"**:保留主机名,还是降级成布尔?
4. **语料入口的可见性**:维持现在的"仅开启调试日志时出现",还是常驻但带确认?
