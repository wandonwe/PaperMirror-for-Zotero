# PaperMirror 文镜 · 最终优化计划（合并 本审计四维 + Codex 审核）

本计划合并两份审核并去重、排批：
- **本审计**（四只读子代理，详见 `功能审核-2.1.6.md`）：逐点实证发现，覆盖性能/API/排版/工作流，并额外覆盖**导出 PDF builder** 与 **UI 入口**。
- **Codex 审核**：抓住主线——**「页面并发」与「真实 HTTP 请求并发」未统一**，是当前卡顿、429、API 浪费与新页等待的总根因；并给出请求级调度、自适应预取、表格语义、刷新本页拆分四项发布前必做项。

发布策略（采纳 Codex 建议）：**继续作为 Beta**；完成「第一批止血 + 第二批架构核心」后再对外称「高性能稳定版」，且以第五批的真实性能基线验证后为准。

标注：`[Codex]` = Codex 提出；`[本审计]` = 四代理提出；`[两者]` = 双方独立命中。所有 `文件:行` 实施前会各自复核。

---

## 冲突与取舍（合并决策）

1. **并发主线优先**：Codex 的两层调度是全局主线，本审计的三条 S 级速赢（willReadFrequently、pmProbe、maxOutputTokens）与之正交，并入「第一批止血」先发。
2. **表格单元格**：Codex 找到根因（单元格 `type` 写成 `paragraph`，`type==='table'` 的布局/高风险路由不识别 → 被混进正文请求），本审计只见症状（整格回退英文）。**采用 Codex 根因方案**（引入 `table-cell`），本审计 LO-8 的「逐 member 兜底」并入其细节。
3. **「刷新本页」行为**：Codex 发现圆环刷新会**自动轮换服务商 + 绕过段落缓存整页重译**（本审计漏项），采纳其「拆三档」，与本审计 WF-6（单段重译可发现性）合并。
4. **导出 PDF 一揽子**：Codex 未覆盖导出 builder。本审计的 LO-1（涂白截断**丢正文**，正确性）/LO-4/5/6/8 整体**下调到后批**——因导出当前无界面入口、触达面小；但进批后 LO-1 排第一。
5. **默认并发**：采纳 Codex 的过渡措施——两层调度落地前，默认全局并行页 12 → 6–8。

## 第五批 · 性能回归基线（发布「高性能稳定版」的门槛 · Codex 第三阶段收尾）

- 用 **20 篇代表性 PDF** 建基线并入 CI，记录：当前页首屏时间、整页完成时间、API attempts、token、页/段缓存命中率、补救率、排版成功率、峰值内存。
- 现仅有功能/布局回归测试、无真实性能基线；本批补齐后，前述各批的收益方可用真实数据确认，而非架构推算。

## 预期收益（Codex 架构推算，需第五批基线验证）

完成第一、二阶段（本计划第一~二批）后，保守预估：顺序阅读 API 请求 −20%~40%；快速跳页无效请求 −40%~70%；当前页可见时间 −20%~35%；表格密集页漏译/错位/补救明显下降。
