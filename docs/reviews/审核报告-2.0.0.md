## P0

### P0-1 【实测】`successCodes: false` 让所有传输层失败变成"不可重试的 HTTP 0"

**位置**:`src/translation/providers/httpClient.ts:126`(`successCodes: false`)→
`:147-155`(原样返回 `response.status`)→ `:242`(`requestJSON` 的 `status<200` 分支)
→ `src/translation/errors.ts:39`

**机理**:`Zotero.HTTP.request` 的 `successCodes: false` 语义是**任何状态码都 resolve**,
包括 XHR 的 `status === 0`(DNS 失败、连接被拒、TLS/代理失败、离线、`xhr.abort()`)。
于是 `:157` 那个把网络错误映射成 `NETWORK{retryable:true}`、把 abort 映射成
`CANCELLED` 的 catch 分支**永远不会执行** —— 请求"正常"返回 `{status:0, text:''}`。

**运行时实测**:

```
mapHTTPError(0, '') → code: UNKNOWN | retryable: false
  msg: "Unexpected API response (HTTP 0): "
```

**后果(两条,后一条更严重)**:

1. **网络错误从不重试**。`countedTranslate` 判 `!err.retryable` → 立即抛出,
   `REQUEST_RETRIES` 请求级重试完全失效;`laneFeedback` 收不到 `'rate'`/`'timeout'`,
   自适应限流全程失明。用户看到 "Unexpected API response (HTTP 0)" 而非"网络错误"。
2. **空闲看门狗被打废**。`translationManager.ts:1130-1152` 的 idle watchdog
   `local.abort()` → `xhr.abort()` → resolve status 0 → 抛出 `UNKNOWN` 而非
   `CANCELLED` → `:1148` 的 `e.code === 'CANCELLED'` 判定不成立 → 那段设计好的
   "Page N made no progress for 150 s. Use 重新翻译 to retry" 的 `TIMEOUT` 转译
   **永远不会发生**。

**佐证**:同文件的 XHR 回退路径(`:215` `xhr.onerror` → `NETWORK{retryable:true}`)
是**正确**的。两条路径行为不一致,恰好证明主路径与作者意图不符。

**影响面**:全部引擎,含默认的 bing-free。

**修复**:`send()` 在 Zotero.HTTP 分支返回前显式判 `status === 0`:
`signal?.aborted → CANCELLED`,否则 → `NETWORK{retryable:true}`;
并在 `mapHTTPError` 加 `status <= 0` 的 `NETWORK{retryable:true}` 分支作二道防线。

### P0-2 【实测】「诊断」按钮把整页原文复制到剪贴板 —— 与项目硬性不变量冲突

**位置**:`src/reader/readerSession.ts:1866`(`currentPageCorpus: this.layoutCorpus()`)、
`:1906-1925`

```ts
items: page.items.map(i => ({ text: i.text, rect: i.rect, ... }))   // 当前页全部原文 span
source: adapter.getReaderItem(this.reader)?.getDisplayTitle?.()      // 文献标题
```

**为什么是问题**:项目的硬性约束是「原文与译文绝不进入日志或诊断」。代码注释
(`:1864`)自认「与「语料」按钮合并」,而全仓已无独立的语料导出入口 —— 于是这条
不变量的**唯一例外被并进了通用诊断按钮**。同时三处文档自相矛盾:
`translationManager.ts:818` 的 `exportDiagnostics()` 注释仍写 "no source text",
`translationPane.ts:132` 的回调注释写 "sanitized per-page diagnostics JSON"。

**场景**:用户为提交 bug 打开调试日志 → 出现「诊断」按钮 → 在一篇未公开的投稿
PDF 上点击 → 剪贴板得到含该页全文 + 文献标题的 JSON → 粘贴进 GitHub issue。
按钮文案主打「诊断」,用户在"提交诊断"的心智下不会预期它含全文。

> **注意**:本项目的日常调试**正依赖**这个语料(本会话多轮 bug 修复都靠它)。
> 因此**不建议直接删除**,应改为知情同意:诊断默认不含语料;语料作为独立按钮
> 或显式勾选项,点击时明确提示"将包含本页原文"。

**日志侧已验证成立**:`logger.emit/remember` 均先过 `sanitize()`;全仓仅 3 处绕过
logger 直呼 Zotero 日志(`preferences.ts:92/97/906`),其中 2 处静态字符串;
`httpClient.ts:117-125` 与 `pdfService.ts:100` 都设了 `logBodyLength: 0`。

### P1-3 【实测】默认引擎 bing-free 的 Edge 兜底绕过用户 Base URL,把原文发往硬编码微软端点

**位置**:`src/translation/providers/bingFree.ts:43`(`EDGE_AUTH_URL`)、`:51`
(`EDGE_API_URL`)、`:245`(兜底调用);默认引擎见 `prefs.js:8`

`translateViaScrape` 尊重用户的 Base URL 覆盖(`resolveBingApiBase`),但一旦它抛错,
`:243-247` 静默落到 `translateViaEdge`,而后者的 URL 是**硬编码常量**
`api-edge.cognitive.microsofttranslator.com` / `edge.microsoft.com`,
**完全不读 `settings.apiBaseURL`**,请求体是论文原文。

**场景**:机构用户把 bing-free 的 Base URL 指向自建代理 `https://mt.corp.internal`
正是为了让论文不出内网。代理返回一次 502 → 同一段原文立刻被 POST 到微软端点。
UI 上只有译文正常出现,**无任何提示**。隐私提示卡只展示一个主机,与实际出站主机
集合不符。

**修复**:用户设置了非 bing.com 的 Base URL 时禁用 Edge 兜底(或要求显式许可);
隐私卡改为列出该引擎可能触达的全部主机。

### P1-4 【实测】Ollama 无条件放行明文 HTTP,绕过 `allowHTTPEndpoint` 门槛

**位置**:`src/translation/providers/registry.ts:109`

allowInsecureHTTP: () => true   // 注释:"localhost only by default URL"

### P1-5 【实测】HTTP 错误消息带回响应体片段,且 UI 路径未经脱敏

**位置**:`src/translation/errors.ts:9/33/36/39`(拼入前 200 字节响应体)→

### P1-6 【实测】`compressPending` 在渲染被取代时永久泄漏 → 该页排版状态机死锁

**位置**:`src/reader/readerSession.ts:1211-1221`

```ts
.then((accepted) => {
    if (!live()) { return; }              // ← 早退,不清理
    ...
    this.compressPending.delete(pageIndex);   // ← 只在 live 路径清理
})
.catch(() => { this.compressPending.delete(pageIndex); ... });   // catch 却清理了
```

**这个不对称本身就是证据**:catch 分支清理、then 的早退不清理,显然是遗漏。

压缩请求飞行中(可达 120 s)时该页被重渲染或卸下 → `live()` 假 → `pageIndex`
永久留在 `compressPending`。此后该页任何渲染进入 `resolveStrictUnfit`(`:1198`)
直接 return,且 `:1201` 的第二个条件恒假 → **`reportPlacement` 永不执行**:
几何复核不跑、tally 不产出、胶囊停在「正在适配排版」、未适配块永远显示英文且不计数。

**场景**:压缩飞行中向下滚 3 页(`releaseFarSlots` 换 ghost)或拖分栏条
(`relayoutSlots` 清 slot)。回到该页 —— 永久卡住,只有手动「刷新本页」能恢复。

**修复**:`delete` 移到 `.then` 第一行(`live()` 检查之前),或改用 `.finally()`。

### P1-7 【实测】`splitView.applyRatio` 的自续定时器无界、无 destroy 守卫

**位置**:`src/reader/splitView.ts:139-141`

```ts
if (total < 50) {
    (doc.defaultView ?? globalThis).setTimeout(() => applyRatio(ratio), 50);  // 无句柄/无计数/无 destroyed 判断
    return;
}
```

**实测**:`destroyed` 变量只出现在 `:248-253`(destroy() 自身),`applyRatio`
**从不读它**。

Zotero 隐藏非选中标签的容器 → `getBoundingClientRect().width === 0` → `total < 50`
恒成立 → 链永不终止。而 `readerSession` 每 350 ms 调 `refreshLayout()` → 每 350 ms
**新增一条 20 Hz 链**,互不取消。

**后果**:(a) 后台 5 分钟 ≈ 857 条链 ≈ 每秒 1.7 万次强制重排,UI 卡顿;
(b) `logger.warn` 每 350 ms 一条,约 13 秒冲光 40 条环形缓冲,
`Zotero.PaperMirror.lastErrors()` 里真正的错误被挤掉;
(c) destroy 后残链仍执行 `style.setProperty(..., 'important')`,把已恢复的阅读器
**重新钉死在 50% 宽**,只能关标签页恢复。

### P1-8 【agent,含运行时复现】「刷新本页」/快速翻页被"已中止但仍在 active"的旧任务挡回

**位置**:`src/translation/translationManager.ts:745-750`、`:1017-1019`;
`src/translation/requestScheduler.ts:204-215`

`retranslatePage` 的 `pages.delete()` → `scheduler.cancel()` → `ensurePage()` 三步
**无 await**,而 `cancel()` 对运行中任务只发 abort,从 `active` 移除发生在
`execute()` 的 `finally`(异步之后)。于是 `ensurePage` 同步走到 `isScheduled()`
时旧任务仍在 active → **early-return**。此时页面状态已删、新任务未入队,两头落空。

审计通道用真实源码 bundle 复现:
`state before refresh: translating` → `state AFTER 刷新本页: (no state at all), translateCalls = 1`。
同一机理还影响 `restartAfterConfigChange`(切换服务商后当前页不自动重翻)。

**修复**:`cancel()` 里对 active 任务立即 `this.active.delete(key)`,或提供
`cancelAndWait(key)` 供调用方 await。

### P1-9 【agent】配置切换瞬间,旧引擎译文被写进新引擎的缓存键

**位置**:`translationManager.ts:1797-1805`(`persistPartial`)+
`readerSession.ts:654-669`(`segmentContext` **在写入时刻**才读 pref)+
`:1615-1636`(`applyProviderPick` 先 `setPref` 再 `resetAll`)

缓存身份不是在**产出译文时快照**的,而是在**落盘时**现读 pref。`resetAll()` 触发的
取消恰好会走到 `persistPartial()`,此时 provider 已被改成新引擎 → A 的译文写进 B 的
段落库,重启后依然如此。

**修复**:`translatePage` 开始时一次性快照 `CacheKeyParts`/`SegmentContextParts`,
整个页面生命周期复用。

### P1-10 【agent】术语表 / 不译词改动不会让页面缓存失效

**位置**:`cacheSchema.ts:20-33`(`CacheKeyParts` 无 `glossaryHash`)vs `:124-132`
(`SegmentContextParts` **有**);`translationManager.ts:1362-1389`(页面缓存完整命中
直接 return,走不到段落层)

段落 context 里放了 `glossaryHash` 说明作者意图是"改术语表要失效",但页面缓存是
先命中的一层且键里没有它 → 该意图对**所有已翻译页面**完全落空。不译词列表更彻底:
两层都不含。

**场景**:用户把 "transformer" 加进术语表 → 重开 PDF → 每页命中页面缓存 →
**术语表一个字都没生效**,用户会认为功能坏了。

## 2. 已验证成立的不变量(未发现破坏)

- **模型输出只经 textContent 渲染**:全仓 `innerHTML`/`outerHTML`/`insertAdjacentHTML`/
  `document.write`/`createContextualFragment`/`eval`/`new Function` 命中数 **0**。
  唯一 `DOMParser`(`translationPane.ts:489`)解析的是构建期 inline 的品牌 SVG 常量,
  且校验 `documentElement.nodeName === 'svg'`。笔记路径 `escapeHTML` 覆盖 `& < > " '`
  且每个插值位(含 href)都过了它。
- **缓存文件不含密钥**:缓存结构与文件名生成逐字段核对,无密钥字段。
- **无遥测**:全仓无 `sendBeacon`/analytics/sentry,所有出站主机均为翻译服务或文档链接。
- **写入原子性**:所有落盘都用 tmpPath + rename,读侧看不到半截文件。
- **`enqueueWrite` 队列逻辑本身正确**:`prev.then(job, job)` 保证失败不卡死;
  读 prev 与 set next 之间无 await,不存在插队;不同路径互不阻塞。
- **1.3.0 的页面缓存完整性校验无回归**:逐字段比对 + 形状校验 + `accept()` 二次验收 +
  部分命中只 prefill,这套修复是扎实的。
- **Notifier 注册/注销配对**、**shutdown 注册表 LIFO + 独立 try/catch**、
