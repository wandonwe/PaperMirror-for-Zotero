# 性能基线 · 操作指南(优化计划 第五批)

第五批的目标:为「高性能稳定版」建立**可复现**的性能基线,让第一~四批的收益用
数据确认而非架构推算。基线分两半 —— 离线半自动进 CI,真实世界半用采集器汇总。

## 一、离线基线(已入 CI,零操作)

`tests/integration/pipelineBaseline.test.ts` 对仓库内 12 页真实 PDF 语料
(`tests/fixtures/layout/*.spans.json`,8 篇文档:双栏医学/表格密集/NEJM 等)跑与
运行时同构的确定性流水线,把**请求计划形状**锁进
`tests/fixtures/baseline/pipeline-baseline.json`:

- blocks / translatable / tableCells / modules
- chunks / fastChunks / slowChunks / maxBlocksPerChunk
- payloadChars(请求输入体量代理,≈ token 的稳定代理)
- dupBlocks(API-2 同页去重省下的块)

任何让某页 chunk 数/payload 回涨的改动都会红 CI。**有意的优化**:删基线文件重跑
`npm test` 重新生成,diff 进 PR 审阅。耗时(环境相关)不进断言,由 `npm run bench`
输出每页中位数耗时作信息性参考。

**扩充语料**(推荐凑满 20 篇文档):在装了插件的 Zotero 里打开目标 PDF,开发者
控制台运行 `scripts/dump-spans.mjs` 的转储入口(或「更多⋯ → 语料」复制当前页
布局语料,需开调试日志),把 `<name>-pN.spans.json` 放进 `tests/fixtures/layout/`;
跑一次 `npm test` 会提示新页无基线,删除基线文件重新生成即可。

## 二、真实世界基线(20 篇 PDF,一次约 1–2 小时)

覆盖面建议(20 篇):双栏 ≥8、表格密集 ≥4、公式密集 ≥3、长文(>20 页)≥2、
扫描/混合 ≥1、封面复杂(结构化摘要)≥2。

每篇的流程:

1. Zotero 打开 PDF → 工具栏开启翻译(对照模式)。
2. **顺序读完**(逐页翻到尾,让预取/缓存按真实节奏工作;首篇前先在设置里
   「清除全部缓存」,保证冷启动口径)。
3. 「更多 ⋯ → 诊断」,把剪贴板 JSON 存为 `诊断-<篇名>.json`。
4. (可选热缓存口径)关闭再打开同一篇重读一遍,再导一份诊断,对比命中率。

全部跑完后汇总:

```
node scripts/baseline-report.mjs 诊断-*.json
```

输出每篇 + 合计的基线表并写出 `baseline-report.md`:页数、请求数、请求/页、
逐块补救、429、超时、段落缓存命中、页均耗时、已译/保留原文块数、排版
placed/kept 与成功率、几何违例。把该文件存入 `docs/reviews/` 即为本版本的基线。

**判定门槛建议**(高性能稳定版):请求/页 ≤ 1.5(顺序读、单引擎、冷缓存)、
排版成功率 ≥ 97%、几何违例 = 0、热缓存重读请求 ≈ 0。

## 三、尚未自动化的两项(手工口径)

- **当前页首屏时间**:开调试日志,取 `Page N: … requests` 行与页进入日志的时间差;
  或秒表实测「翻到新页 → 首段译文可见」。建议抽 5 篇 × 3 页记录中位数。
- **峰值内存**:Zotero 地址栏 `about:memory` → Measure,读完 20 篇后记录
  `zotero.exe` 常驻;对照基线为未开插件读同批 PDF。

## 四、口径备注

- 诊断 JSON 本身即脱敏(不含原文/译文/密钥),汇总脚本纯计数聚合,可放心入库。
- `requests` 是**逻辑请求数**(含重试/补救各计 1 次);429/超时单列。
- 段落缓存命中 (`segHits`) 在冷启动首篇应≈0,跨文档共享库(2.3.5)生效后,
  同领域后续篇目应看到样板句命中 >0 —— 这是 API-3 的直接验证点。
